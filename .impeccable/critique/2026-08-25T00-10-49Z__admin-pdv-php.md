## Design Specificity Verdict

**LLM assessment:** This is a genuine purpose-built POS — real domain features (stock badges, promo pricing, cashback/points, keyboard shortcuts for a checkout counter) — not a generic admin CRUD screen wearing a food-service skin. But its visual layer reads as *unfinished*, not *authored*: it mixes the documented copper system with leftover blue tokens and a different font family from an older admin theme that was never migrated.

**Deterministic scan:** `detect.mjs` against `admin/pdv.php` + `admin/assets/js/pdv.js` + `admin/assets/css/pdv.css` (14,551 combined lines) returned **550 findings** — 5 warning-severity, 545 advisory. ## Overall Impression

The order-building mechanics are more sophisticated than they look at a glance (real shortcuts, sanitized inputs, stock-aware blocking) — this wasn't thrown together. But the single biggest opportunity is closing the gap between the product's largest tap target (the product card) and what it actually does (nothing to the cart), because that gap gets re-paid in lost seconds on every single order, all day, by every cashier.

## What's Working

- **Real POS ergonomics, not just CRUD-with-icons:** F2/F3/F4/Ctrl+Enter shortcuts and Enter-to-commit search (`pdv.js:4484-4503`, `3040-3048`) are the kind of detail that only shows up when someone actually thought about a busy counter.
- **Defensive input handling:** quantity fields are debounced and digit-sanitized with a length cap (`pdv.js:2974-2981`); out-of-stock items are blocked pre-emptively with a specific toast rather than failing at submit.
- **23 `aria-label` attributes present** — accessibility wasn't ignored, just not finished (see Persona: Sam below).

## Priority Issues

**[P0] Product card tap doesn't add to cart**
- **Why it matters:** The photo/name/price card is the largest, most obvious tap target on the screen — a cashier under pressure will tap it expecting an add. Instead it only toggles a `.active` "selected" visual state (`pdv.js:2523-2549`); the actual add only happens via the small `+` button or by typing a quantity (`pdv.js:3005-3017`). Repeated dozens of times a shift, this is real lost time and mis-clicks.
- **Fix:** Make tapping the card body (outside the qty stepper) increment quantity by 1, matching what the `+` already does. Keep the stepper for adjusting past 1.
- **Suggested command:** `/impeccable layout`

**[P1] Order-type and customer search are filed under the wrong mental category**
- **Why it matters:** The order-type dropdown sits inside a card titled "Pagamento / Etapa 2" (`pdv.php:718-721`) though choosing delivery/pickup/dine-in isn't a payment decision — and customer search is wrapped in a `.pdv-retirada` (pickup-specific) class even though every order type needs it (`pdv.php:752, 799`). This is a real match-the-user's-model failure (heuristic 2) that also makes the CSS harder to reason about.
- **Fix:** Split into a distinct "Pedido" (order) section (type + customer) and a separate "Pagamento" section (method, split, troco).
- **Suggested command:** `/impeccable clarify`

**[P1] PDV was never brought under the documented design system**
- **Why it matters:** 469 of 545 detector findings are undocumented colors in `pdv.css` alone, 7 of them literal leftover blues (`#1d4ed8`, `#3b82f6`, `#eff6ff`, `#dbeafe`) against the copper-only system, and the page's actual font (`Manrope`) isn't `Poppins` and isn't declared anywhere. On the highest-traffic screen in the product, this reads as visually unfinished/inconsistent rather than deliberate.
- **Fix:** Re-map the 7 blue instances to the existing `state-success`/`state-error`/`copper-primary` tokens where they're semantic, or extend `DESIGN.md` deliberately if `admin/` is meant to be a documented second surface (it currently isn't — `DESIGN.md` only covers `public/`).
- **Suggested command:** `/impeccable document` (to properly scope/extend the design system to `admin/`), then `/impeccable polish`

**[P2] Right-side panel crams 8+ unrelated control groups into one scroll**
- **Why it matters:** Order type, print settings, scheduling, customer card, delivery card, 8 payment fields, and two cashback/points toggles all live under one "Pagamento" card (`pdv.php:711-1052`) — well past the ≤4-items-per-group chunking guideline, and it's the panel a cashier's eyes return to after every single item add.
- **Fix:** Collapse agendamento/cashback/points into accordions that only expand when relevant to the current order type.
- **Suggested command:** `/impeccable layout`

**[P2] Accessibility gaps on the cart's live state**
- **Why it matters:** Only 1 `aria-live` region exists across the whole page/JS, and cart totals (`resumoItens`) update with no announcement — a screen-reader user gets zero auditory confirmation that an add worked. There are also 26 more `<input>` elements than `<label>` elements in `pdv.php` (67 vs. 41), suggesting some inputs lack accessible names.
- **Fix:** Add an `aria-live="polite"` region around the cart summary/total; audit the 26-input gap for genuinely unlabeled fields (not all may need one — hidden/decorative inputs are legitimate — but the gap is worth a pass).
- **Suggested command:** `/impeccable harden`

## Persona Red Flags

**Alex (impatient cashier, power user):** Taps product photos expecting an instant add and gets a silent "selected" state instead (`pdv.js:2523-2549`); hunts for the order-type control inside a card literally labeled "Pagamento" (`pdv.php:718-721`); typing a quantity requires blur/Enter to commit (`pdv.js:2982-2997`) — one extra beat versus a direct tap-to-increment Alex expects from every other POS he's used.

**Sam (accessibility-dependent, screen-reader/keyboard-only):** No `aria-live` region means cart adds are invisible to a screen reader (confirmed: 1 occurrence sitewide, not tied to the cart). 26 more inputs than labels in `pdv.php` means some fields likely lack accessible names. The mixed blue/copper palette (`pdv.css:2701-2726, 4523-4524, 4900`) suggests contrast was never audited as one system — color-only distinctions were avoided elsewhere (icon+text pairing on stock states), which is good, but it's inconsistent rigor.

## Minor Observations

- 3 `<img src="">` placeholders in the edit-item modal (`pdv.php:1879, 1949, 2012`) can flash a broken-image icon before JS populates them — worth a `data-src` pattern or a default placeholder image instead of an empty `src`.
- `pdv.css` has 201 `!important` declarations — a specificity-war smell that will make any future restyle (including bringing this file under `DESIGN.md`) harder than it needs to be.
- Combo/variação product cards silently make the qty input read-only (`pdv.js:2961-2969`) with only a tooltip `title` — no visible visual affordance distinguishes them from simple products until you try to type in the field.
- "Somente promo" (a filter) and "Item avulso" (an action) share a row (`pdv.php:585-592`) despite being unrelated types of control — easy to mis-scan at speed.
